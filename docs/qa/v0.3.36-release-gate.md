# 0.3.36 security maintenance release gate

Candidate scope: application-level distrust of the eight compromised emSign
SPKIs on Electrum and HTTPS, refreshed native advisory applicability from PR
#107, and versionName 0.3.36/versionCode 336. Dependencies, native library bytes,
database schema, wallet/signing/transaction logic and release-signing policy are
unchanged. The production design and identity evidence are documented in
`docs/security/android-emsign-distrust.md`.

Acceptance requires the exact candidate's full JVM suite, debug/unsigned release
assembly and lint, plus the exact 13-case network matrix on API26 AOSP and API35.
Existing Android restart, migration, persistence and 59-case instrumentation
contracts must pass too. New network cases exercise completed paths, omitted
cached intermediates/anchors, same-key reissues/cross-signs and pin rejection
before any decrypted application payload. Independent static test review is
not a substitute for real Android execution.

The source-bound native gate must query all candidates, verify all exact live
advisory contents and account for all 17 reviewed matches with the unchanged
November 8 expiry. The application digest includes this version change and
the reviewed transport delta. Maintenance acceptance is not proof that the
unmaintained build tool is fixed or complete native assurance is established.

Before signing, the unchanged protected release workflow must verify the
annotated maintainer-signed tag against exact current protected master, run its
strict checks and prove blind raw-byte unsigned reproducibility. Source-free
isolated signing and separate post-sign equivalence must pass. Publication must
create a new v0.3.36 release, never replace an existing release. Public-download
verification must pass before website version references are updated/deployed.

Actual run status, source identities and URLs belong in workflow receipts and
the execution checkpoint; this gate document does not assert unfinished test,
merge, signing or publication outcomes. Broader physical hardware-wallet
acceptance and SQLCipher source-to-binary correspondence remain separate.
