# Clench Wallet 0.3.24

Clench Wallet 0.3.24 is a security-hardening release. It closes gaps found in
an end-to-end review of wallet creation, external signing, authentication,
network transport, NFC/QR/file imports, local storage, and release signing.

## In plain English

- New Clench seeds are generated from explicit Android operating-system
  entropy. The app fails closed if secure randomness is unavailable and wipes
  the temporary entropy bytes after use.
- External hardware-wallet returns are accepted only when their signatures
  commit to the complete reviewed transaction. Weak or unexpected sighash
  policies are rejected before merge, finalization, or broadcast.
- Clench now copies only verified signature material from a returned PSBT into
  the original transaction instead of trusting the returned container.
- Seed creation and verification remain protected from screenshots, screen
  recording, Recents previews, and obscured-window touches for the complete
  flow.
- PIN and device-authentication controls fail closed. PIN throttling uses
  monotonic time and detects device restarts rather than trusting the wall
  clock.
- Authentication results are bound to the current prompt and foreground
  generation. Stale biometric callbacks cannot unlock the app or approve a
  protected wallet action.
- When Clench backgrounds, it stops admitting new secret/signing work, drains
  active operations, closes native wallet state, and then locks. A failed
  native close or secret-cache deletion requires an app restart rather than
  reopening the wallet in an uncertain state.
- Electrum TLS connections remain encrypted for every request path. Onion
  servers are routed through Tor even when the hostname uses unusual casing or
  a trailing dot.
- NFC, QR, UR, BBQr, PSBT, backup, and descriptor imports have stricter size,
  type, session, and private-key checks.
- TAPSIGNER setup verifies the factory identity, nonce transcript, expected
  derivation path, public key, xpub, and chain code. A fresh app-secret digest
  is encrypted inside an authenticated `sign` command and must be signed by the
  selected account key before its xpub is accepted. This prevents an NFC relay
  from substituting an attacker-controlled receive key. A direct controlled
  tap and out-of-band fingerprint/address check remain required because Tap
  Protocol does not sign every path and serialization metadata field.
- The release workflow accepts only a pinned maintainer-signed tag on the
  approved protected-master commit. Source builds occur without signing
  secrets; a minimal isolated job signs only a verified unsigned APK.
- Exact release dependencies are checked against OSV, and reviewed exceptions
  must be narrow and expire.

## Coldcard entropy incident boundary

The review did not find a Coldcard-style deterministic fallback in Clench.
Clench does not manufacture hardware-wallet seed entropy and cannot determine
from an imported xpub whether another device originally generated a weak seed.
Users of firmware covered by a hardware vendor's entropy advisory must follow
that vendor's migration instructions independently of this release.

This update does not, by itself, require owners of Clench-generated wallets to
replace their seeds. High-value multisig policies should continue to use keys
created independently on different devices.

## External signer safety

The v0.3.23 review found that a malicious hardware-wallet return could carry a
signature that did not commit to every reviewed output. v0.3.24 rejects that
condition across PSBT metadata, ECDSA and Taproot signatures, final witnesses,
scriptSigs, and finalized raw transactions. ECDSA returns must use
`SIGHASH_ALL`; Taproot returns may use only `DEFAULT` or `ALL`.

The Advanced Tools raw broadcaster also rejects recognizable weak signature
flags before connecting to the network. Raw transactions do not contain their
spent outputs, original PSBT, or wallet policy, so this context-free check
cannot prove as much as the hardware-signer return flow. Prefer the PSBT
coordinator; Clench warns about this boundary and may reject unusual scripts
conservatively.

On 2026-08-04 the maintainer reported completing physical-device checks and
authorized this release. Device-, firmware-, transport-, and APK-specific
row evidence was not supplied to the repository, so the physical matrix keeps
its individual rows as `NOT RUN` rather than inventing pass records. Automated
hostile fixtures prove parser and policy behavior but do not substitute for
auditable real-device evidence.

## Release and platform boundaries

The build, reproducibility, signer-continuity, SBOM, provenance, dependency,
and no-secrets verification controls remain mandatory. The repository can pin
the authorized source-tag key and isolate the APK signing job, but the current
GitHub organization still has a single maintainer identity able to administer
the repository and approve its signing environment. A separate approval
identity and offline or hardware-held release key remain recommended
operational controls outside this source change.

Hardware-backed Android Keystore properties vary by device. Clench reports the
observed security level and no longer promises that every supported phone uses
StrongBox or another hardware module. Public wallet state such as xpubs,
scripts, balances, and transaction history remains sensitive metadata even
though spending secrets are stored separately.

## Physical-test boundary

The maintainer-reported physical checks and explicit ship authorization are
recorded in `docs/qa/physical-hardware-gates-v0.3.24.md`. Because the report did
not include row-level evidence, the SATSCARD, TAPSIGNER, hardware-wallet,
NFC/camera, biometric, Keystore, upgrade, process-kill, and removable-media
rows remain `NOT RUN`; no row-specific physical pass is claimed. PIN/CVC
change and direct TAPSIGNER payment/cosigner signing remain unimplemented.
