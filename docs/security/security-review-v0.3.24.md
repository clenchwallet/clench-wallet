# Clench Wallet 0.3.24 Security Review

This document records the in-repository disposition of the security review
performed against v0.3.23 and the corresponding v0.3.24 release candidate. It
is not a substitute for an independent professional audit or physical-device
testing.

## Scope

- seed entropy and signing nonces;
- transaction construction, PSBT exchange, signature policy, and broadcast;
- QR, UR, BBQr, NFC, SATSCARD, TAPSIGNER, and file inputs;
- authentication, PIN throttling, screenshots/Recents, overlays, storage,
  backup, corruption, and recovery;
- Electrum, HTTPS, Tor, and own-node configuration;
- Android manifest/package attack surface and exact dependencies;
- reproducible builds, provenance, SBOM, tag trust, APK signing, and independent
  release verification.

## Resolved release blockers

| Finding | v0.3.24 disposition |
| --- | --- |
| External signer return could contain a weak signature-hash policy | Reject every non-ALL ECDSA signature and every non-DEFAULT/non-ALL Taproot signature in PSBT metadata, partial signatures, final stacks, and raw transactions; merge only approved signature fields into the canonical PSBT |
| Seed verification could lose capture protection | Ref-counted secure-window protection covers creation and verification; obscured touches are rejected globally and on sensitive controls |
| Source tag and release-key isolation were insufficiently bound | Pinned maintainer tag key, exact protected-master commit requirement, no-secrets unsigned build, minimal isolated APK signer, signing-material destruction, independent rebuild, and pre-publication tag re-verification |
| Backgrounding could race secret-bearing native wallet operations | A process-wide admission barrier drains foreground secret/signing operations before cache eviction; failed native cleanup is quarantined and latches a restart-required state instead of reopening protected navigation |

## Additional hardening

| Area | v0.3.24 disposition |
| --- | --- |
| Seed entropy | App-owned injectable `SecureRandom` produces explicit 128/256-bit entropy, fails closed, and wipes temporary bytes |
| Electrum transport | All TLS modes use hostname-verified TLS; plaintext is explicit; onion variants route through Tor without local DNS |
| Authentication | Unavailable/cancelled Android authentication remains locked; cryptographic proof is bound to the current prompt and lifecycle generation; stale callbacks cannot authorize an action; PIN delays use monotonic time and reboot detection |
| Imports | Bounds and canonical/type/session checks cover PSBT, QR/UR/BBQr, NFC, descriptor, and backup paths before expensive allocation or state mutation |
| Watch-only backup | Mainnet and testnet private descriptors are rejected structurally and by explicit extended-private-key prefixes |
| Signing authorization | Wallet/session/unsigned-PSBT identity is immutable, duplicate operations are serialized, and stale callbacks fail closed |
| Raw transaction tool | Recognizable weak ECDSA and Taproot signature flags are rejected before network broadcast; the UI explains that a raw transaction lacks the prevouts and original policy needed for the coordinator's stronger proof |
| Native lifecycle | Import, creation, seed viewing/backup, repository, and sweep/signing paths share foreground admission and deterministic cleanup; every cleanup is attempted, failures are retained for process lifetime, and sensitive temporary files must be verified deleted |
| TAPSIGNER | Factory identity, nonce transcript, derivation, public key, xpub, and chain code are checked; a fresh encrypted challenge proves possession of the selected account key; sensitive working buffers are cleared |
| Storage | Public-state and secret-storage claims are separated; passphrase caches fail closed on incomplete deletion; Keystore capability is reported rather than assumed |
| Android surface | Unused Bluetooth and browsable surfaces are removed; FileProvider exposure is narrowed to the export directory |
| Dependencies | Bouncy Castle runtime is updated; exact Maven components are checked against OSV with expiring reviewed exceptions only |

## Entropy conclusion

The reviewed Clench seed-generation path did not contain the deterministic
fallback class involved in the Coldcard firmware incident. v0.3.24 no longer
relies on an implicit library constructor: it obtains explicit bytes from
Android's secure operating-system RNG and passes those bytes to BIP39.

This conclusion applies only to seeds generated by Clench. An imported xpub
does not prove that the originating hardware or software used sound entropy.
Users affected by a hardware vendor advisory must follow that vendor's
migration guidance.

## Residual risks and required evidence

- The GitHub organization currently has one maintainer identity that can both
  administer the repository and approve its signing environment. Close this
  operational risk with an independent approver and offline/hardware release
  key custody.
- The exact Maven SBOM does not enumerate Rust crates nested inside the pinned
  BDK Android artifact. Track upstream BDK advisories and audit its published
  Cargo lock until nested evidence is available.
- Public certificate pinning is intentionally not imposed on arbitrary
  user-configured Electrum/mempool endpoints. Platform certificate validation,
  explicit TLS configuration, optional certificate pinning for Electrum, and
  Tor remain the compatibility boundary.
- Direct TAPSIGNER transaction signing and PIN/CVC change are not implemented.
  Do not describe watch-only setup/import as payment-signing support.
- The Advanced Tools raw-transaction broadcaster can recognize and reject weak
  flags in ordinary DER ECDSA and Taproot-shaped witnesses, but raw bytes do not
  contain spent outputs, the original PSBT, or wallet policy. It cannot provide
  the external-signer coordinator's full transaction-policy proof. Prefer the
  PSBT return flow; unusual scripts may be rejected conservatively.
- TAPSIGNER proof of possession prevents an active NFC relay from replacing the
  account with an attacker-controlled key. Tap Protocol still does not sign
  every derive-path, master-fingerprint, and xpub-serialization metadata field;
  a relay could cause a recovery/availability failure by steering the genuine
  card to a different account and mislabeling it. Use a direct controlled tap
  and verify the imported fingerprint/address out of band; do not claim general
  relay resistance.
- The pinned BDK interface can cryptographically validate a complete PSBT while
  finalizing it, but does not expose per-signature verification for an
  incomplete multisig PSBT. A syntactically valid but bad partial can therefore
  invalidate the current in-memory signing attempt. Cancel/restart discards it;
  this is a recoverable session denial of service, not durable wallet damage or
  a fund-redirection path. Close it upstream with a pinned bdk-ffi API built on
  rust-bitcoin sighash/interpreter primitives rather than reimplementing
  BIP143/BIP341 consensus logic in Kotlin.
- Physical or instrumentation evidence is still required for Keystore level,
  biometric invalidation, screenshot/Recents behavior, overlay rejection, NFC
  relay/interruption, device-specific parser behavior, hardware-wallet
  round trips, upgrade, and recovery.
